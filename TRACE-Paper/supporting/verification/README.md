# Numerical verification of the current manuscript revision

These read-only recalculations check consistency with local exports, not the
authenticity of raw execution, prospective preregistration, or independent
experimental replication. No experimental input was changed or rerun.

## Post hoc EvoSuite B2 token sensitivity estimate

`evosuite-b2-token-estimate.json` is generated by
`scripts/estimate-evosuite-b2-tokens.py` using `tiktoken==0.14.0`. It tokenizes
the 275 retained EvoSuite test-source files that reached B2. A linear fit on
the 67 no-retry Gemini 3.5 B2 cases in the separate RQ3 study maps source-token
counts to reported input tokens; mean RQ3 output usage supplies an illustrative
output estimate. With `o200k_base`, the result is 7,170,371 estimated input
tokens and 59,330 estimated output tokens, or 7,229,701 in total. Using
`cl100k_base` instead produces 7,302,128 total. Neither tokenizer is Gemini
2.5 Flash's tokenizer; neither result is historical provider usage. The
different model, missing original B2 request/response payloads, retries, and
unobserved thinking tokens prevent a calibrated uncertainty interval or an
observed cost comparison. The manuscript presents the value only as a post hoc
sensitivity calculation, not as the value of `Evo_Tokens`.

Note for the public artifact: three of the 275 EvoSuite test sources contain a
redacted workspace path (`<WORKSPACE>`), so rerunning the script on this
repository gives 7,229,527 (`o200k_base`) and 7,301,958 (`cl100k_base`), about
170 tokens below the recorded values above. The rounded figure in the
manuscript (approximately 7.23 million) is unchanged.

To reproduce from the wider workspace after installing `tiktoken==0.14.0`:

```sh
python3 TRACE-Paper/supporting/scripts/estimate-evosuite-b2-tokens.py \
  --output TRACE-Paper/supporting/verification/evosuite-b2-token-estimate.json
```


## Latest timing audit: extracted EvoSuite campaign

`evosuite-timing-consistency.json` and its adjacent diagnostic CSV check all
450 current command budgets (420 seconds), the measured search-process
`durationMs` and `timestampUtc`, the terminal whole-run duration and timestamp,
and the paired CSV. Every run has pre-compile and search metadata; 275 have
JaCoCo test-run metadata and 233 have PIT metadata. No measured search duration
exceeds its whole-run duration, no stage timestamp falls outside its terminal
run interval beyond the stated one-second tolerance, and each CSV duration
agrees with the terminal duration to its two-decimal precision. The terminal
durations sum to 56.33 hours for EvoSuite (450.63 seconds per run). The audit
establishes internal consistency of the current extracted evidence; it does
not authenticate the execution independently. Experimental inputs were not edited.

Reproduce from the wider workspace:

```sh

  experiments/full-chain/runs/official-150-20260920-r42-r44-v1 \
  --output TRACE-Paper/supporting/verification/evosuite-timing-consistency.json
```

This is an audit, not a repair command. The current terminal records and
primary CSV already contain the updated measured whole-run durations; the
statistical report was recomputed from the current CSV.

## Supplementary archive-command audit: current archive

`full-chain-archive-audit.json` was generated by the standard-library-only
`scripts/inspect-full-chain-archive.py` from the current 9,814,962,042-byte ZIP.
It reads selected entries without extracting or executing the archive. The
archived paired CSV is byte-identical to the analyzed CSV. All 450 unique
EvoSuite command keys match the 450 EvoSuite terminal keys; **all 450 commands
specify `-Dsearch_budget=420`**. Four commands have `TimedOut: True` and exit
code 137; the corresponding terminal records report 480-second process
timeouts. Preserved pre-update command files outside this current archive
specify 60 seconds. The current archive contains the 420-second campaign state.

The 900 terminal records include 275 EvoSuite runs with one verification pass,
but every EvoSuite record reports zero tokens and provider requests. Current
`EvoSuiteAdapter.cs` calls B2 and then hard-codes these fields to zero; current
`OpenAiCompatibleClient.cs` records LLM usage in the budget governor. These
sources explain the accounting defect but are not a verified historical source
snapshot. No missing B2 token total has been reconstructed. No experimental
inputs or reported effectiveness values were changed.

The earlier RQ1 table describes the scope of the numerical script, not all
subsequent inspection. A separate raw-artifact audit linked all 600 RQ1 rows
and inspected coverage/mutation evidence; see
`../../giaotiep/20260927-1428-dungng2808-to-all-cap-nhat-doi-chieu-nguon-rq1.md`.
Gemini token-estimator provenance remains open; calling the counts estimates
does not supply a tokenizer or estimation algorithm.

To repeat the archive inspection from `paper-2` (Python 3.9+):

```sh
python3 TRACE-Paper/supporting/scripts/inspect-full-chain-archive.py \
  experiments/full-chain/runs/official-150-20260920-r42-r44-v1.zip \
  experiments/full-chain/paired-comparison.csv \
  --output TRACE-Paper/supporting/verification/full-chain-archive-audit.json
```

RQ1 continuous differences use decimal subtraction of exported strings before
conversion to floating point; otherwise binary subtraction can split tied ranks.
The signed-rank tests use a normal approximation, remove zero differences,
correct for tied ranks, and do not use a continuity correction.

For RQ2, cost effects consistently use **TGSLR minus comparator**. Relative to
FTMR, rank-biserial correlations are +0.230099, -0.152181, and -0.396970 for tokens,
API calls, and rounds. A rank-based effect can have a different sign from an
arithmetic mean difference. The previous manuscript's three signs used the
opposite convention. Existing TGSLR-FTMR bootstrap mean-difference interval
endpoints were negated/reordered from the previously stated FTMR-TGSLR direction;
they were not regenerated. They remain explicitly unadjusted intervals.

The FullChain wrapper links the original workspace engines; it does not replace
their random-number generator or percentile convention with a different library.
The input has candidate STS/BC/MS, but not candidate CSR/ESR; the latter are not
exported by this wrapper. Delivered VSR/CSR/ESR use fractions; STS/BC/MS in this
CSV use percentage-point units. Multiplying the former by 100 produces the
manuscript's displayed percentages and intervals.
